## 为什么需要一份批卷纪律

AI 批卷有两个典型失败模式：**凭印象扣分**（看到一处不好就整体低评，把能得分的点一起拖下水）和**无证据放水**（「思路正确，给分」却不逐点核对）。官方阅卷体系之所以可信，靠的是三件武器：

1. **逐点独立判分**——每个 point 只看自己的标准，其他部分的错误与它无关；
2. **algorithm 点特殊规则**——考察「步骤组装」的点有单独的拒分清单；
3. **Errors to Ignore**——一张全国统一的「不扣分」清单，保证口径一致。

下面把这三件武器交给 AI（也交给你自己互评时用）。

## 批卷五规则（给 AI 的总纲）

1. **逐点独立**：按 rubric 表逐行判定，每点只依据该点的 Criteria 与 Decision Rules；一个点的得失不横向影响其他点；
2. **必须引用证据**：每个判定附学生代码中的具体行（引用原文），没有证据的给分/扣分无效；
3. **algorithm 点从严**：标 (algorithm) 的点，凡出现下列任一情形即不给分——必需步骤缺失、步骤组装顺序错误、额外代码使结果不正确（如多余打印、错误的前置检查）、混淆 `[]` 与 `.get()`、修改传入的持久数据、void 方法返回了值、改写给定方法头改变参数个数或类型；
4. **Errors to Ignore 先过一遍**：下表中的错误**不作为**任何点的扣分理由；
5. **本地运行为准**：批改意见与学生本地编译/运行结果冲突时，以本地为准（这可能暴露的是 rubric 理解偏差而非学生错误）。

## Errors to Ignore 全表（CED 印刷页 173 官方清单）

以下错误对**所有点**（含 algorithm 点）都不扣分：

| 类别 | 具体情形 |
| --- | --- |
| 无害冗余 | 无副作用的额外代码（如合法的前置检查、空操作） |
| 拼写 | 能从上下文**无歧义推断**的拼写/大小写错误（如 ArayList → ArrayList）——注意：若上下文无法唯一推断（如同时有 G 和 g 两个变量），则不算 |
| 局部变量 | 局部变量未声明（除非题目特别要求）；局部变量声明在块内块外用；局部变量加 public/private 修饰 |
| 修饰符 | 类或构造器头漏写 public；给定方法头重写时改了参数**变量名**（个数与类型不能变） |
| 标识符 | 把关键字用作变量名 |
| 运算符 | 数学符号代替运算符（×、•、÷、≤、≥、`<>`、≠）；`=` 与 `==` 混用；`[]` `()` `<>` 混淆 |
| 长度/大小 | length/size 混用（带不带括号都算此条） |
| 数组 | 引用整个数组时多余的 `[]`；数组声明里多余的 size（`int[size] nums = new int[size];`）；用 `[i,j]` 代替 `[i][j]` |
| 标点 | 结构清晰时的缺分号；缩进清晰时的缺花括号；无参方法/构造器调用漏括号；if/for/while 条件漏括号 |

> 教学价值：不在这张表上的错误不会被自动原谅，但某个得分点会不会因此丢掉，仍看该点自己的判定规则。真正重罚的是「组装顺序」「边界含等于」「返回值类型」这类让结果变错的逻辑。

## 可直接复制的批卷提示词模板

把下面的模板连同对应 FRQ 的评分标准、题目原文、学生答案一起发给 AI（课程里的 `frq-grader` 教练或任何大模型）：

```text
你是 AP Computer Science A 的阅卷员。请严格按以下规则批卷：

【判分纪律】
1. 只依据我提供的评分标准逐点判分；每个点独立判定，与其他点的错误无关。
2. 每个点的判定必须引用学生代码原文作为证据；没有证据的给分或扣分无效。
3. 标注 (algorithm) 的点，出现以下任一情形不给分：必需步骤缺失；步骤组装
   顺序错误；额外代码使结果不正确；混淆 [] 与 .get()；修改传入的持久数据；
   void 方法返回值；改写方法头改变参数个数或类型。
4. Errors to Ignore（对所有点都不扣分）：可无歧义推断的拼写；局部变量未声明
   或加访问修饰符；类/构造器漏 public；方法头重写只改参数名；数学符号代替
   运算符；= 与 == 混用；length/size 混用；[i,j] 代替 [i][j]；结构清晰时缺
   分号/花括号/括号；无副作用的冗余代码。
5. 不要给学生改写代码——只判分、引用证据、指出最有价值的一处修改。
6. 验证行为性描述时，请用题目的示例数据手动追踪学生代码后再下结论。

【输出格式】
Point N: ✓ / ✗ —— 一句话依据 + 证据行
Part (x) 小计：x / y
总分：x / 7（或 5 / 6）
最有价值的一个修改：……

【评分标准】
（粘贴对应 FRQ 的「官方风格评分标准」整节）

【题目原文】
（粘贴题目说明与示例表）

【学生答案】
（粘贴学生代码）
```

## 示范批卷：一份带三处问题的学生答案

以 FRQ1（PlaylistBuilder）part (a) 为例。学生提交：

```java
public PlaylistBuilder(String startingWord)
{
    playlist = startingWord;
    numWords = 1;
    String next = getNextSong(startingWord);
    while (next != null)
    {
        playlist = next + " " + playlist;
        numWords++;
        next = getNextSong(next);
    }
}
```

AI 按模板输出的批卷（示范）：

```text
Point 1: ✓ —— 循环内 getNextSong(next) 的实参 next 正是最近取到的歌，
证据：next = getNextSong(next)（每次推进到最新一首）。
Point 2: ✓ —— while (next != null) 与 null 的比较方向正确，首调在循环前
完成、循环内末尾推进，无死循环。
Point 3: ✓ —— numWords++ 位于循环体内。（注：字段名实为 numSongs，
学生全篇一致使用 numWords；上下文无其他相似标识符，可无歧义推断，
按 Errors to Ignore 处理，不扣分。）
Point 4: ✗ (algorithm) —— 步骤组装错误：playlist = next + " " + playlist
把新歌插到最前面，用示例数据追踪两轮得 "Gold Highway Sunrise"，
与规格 "Sunrise Highway Gold" 顺序相反。algorithm 点不给分。
Part (a) 小计：3 / 4
最有价值的一个修改：把拼接方向改为 playlist += " " + next;（新歌接到末尾）。
```

注意这份批卷的三个细节：Point 3 的命名问题**给了分**（ignore 清单第 2 行，且说明了为什么可推断）；Point 4 拒分引用了**追踪证据**而不是「感觉不对」；最后只给**一处**修改建议——不改写学生的代码。

## AI 批卷的边界（人工复核点）

AI 批卷可靠的前提是 rubric 够具体，但以下情形建议人工复核：

- **ignore 清单的边界判断**：「可无歧义推断」本质是人的判断，AI 有时过严有时过松（示范里的 numWords 就是这类）；
- **并列返回任意下标**类题目（FRQ4/8）：AI 可能因为与学生答案的下标不同而误判错——rubric 已明示任意即可，复核时留意；
- **编译错误的连锁反应**：学生代码有一处编译错误时，后续代码全都没跑过，AI 需要按「就代码书面形态判分」处理，这与人脑阅卷一致，但值得提醒它在评语中注明；
- **本地运行结果冲突**：学生声称本地输出与 AI 追踪不符时，先信本地——让 AI 重追踪而不是让学生改结论。

把这页与任何一道 FRQ 的评分标准一起发给 AI，就能得到口径稳定的批卷；给自己批卷时同理——先逐点、再给证据、最后才看总分。
