## P3 是什么

学校食堂的校园卡系统：每张卡有卡号和余额，能充值、消费（余额不足拒绝）、查余额。规模感：**一个系统、两类角色、十几个同构方法**——重复度极高、难度受控，正是 Unit 3 类设计的最佳练兵场。

和 P2 的关键区别：**多类协作**。P2 是一个大类包打天下；P3 里 `Account` 类管好自己的钱，`CanteenApp` 的 main 负责开卡、指挥交易——**每个类只操心自己的事**，这正是封装思想在项目层面的样子。

## 模块分解与规格书

```
CanteenApp（指挥调度）
├── main：开 3 张卡 → 模拟一天的消费 → 打印对账单
│
Account（一张卡的自我管理）
├── 字段：id（卡号）、balance（余额）
├── deposit(amount)：充值，无脑加
├── spend(amount)：余额足够才扣款，返回成功与否
└── getId / getBalance：只读通道
```

`Account.spend` 的规格书（照 P1 模板写）：

- **输入**：`amount`（double，本次消费金额）；
- **输出**：余额足够返回 `true` 并扣款，不足返回 `false` 且余额纹丝不动；
- **边界**：amount 恰好等于余额时应该成功（大于等于）；负数金额不在本题范围。

## 验收与抽查

1. **跑通**：对账单三个数字与预期一致（8.0 / 55.0 / 0.0）；
2. **边界抽查**：口头回答——a3 第一次消费为什么成功（5.0 >= 5.0，恰好等于按边界规则放行）？第二次为什么失败、失败后 balance 变了吗？spend 的判断为什么是大于等于而不是大于？
3. **抽查讲解**：随机指 spend 或 deposit 的一行，讲清它读写的是谁的字段、为什么这个方法没有 static。
