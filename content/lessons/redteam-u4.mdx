## 红队日 2.0：从抓虫到埋虫

红队日①你给 AI 埋过虫。今天的终局版是**同学互埋**：你写的虫要骗过另一个人，还要能在他的反击里活下来。规则：

1. 每人埋一只 U4 虫型（越界 / 位移 / 行列混淆 / 读空文件 / off-by-one 任选）；
2. 互换代码，5 分钟抓虫，说出病根三句话；
3. 全对者胜；都没抓到——埋虫者胜，但要现场讲解为什么这只虫这么隐蔽。

先热身。

## L1 热身：两虫连发

```java
// 意图：把 0 到 4 追加进列表（预期 size 5 后结束）
ArrayList<Integer> list = new ArrayList<Integer>();
for (int i = 0; i < list.size(); i++) {
    list.add(i);
}
```

<MultipleChoice id="rt4-l1-grow" question="这段代码的运行表现是什么？列表最终是什么？" options={[{id:'a',label:'列表最终是 [0, 1, 2, 3, 4]'},{id:'b',label:'死循环，内存被慢慢吃满'},{id:'c',label:'编译错误'},{id:'d',label:'正常结束但列表是空的'}]} answer={['d']} explanation="循环条件每轮读的是**当前** size：开始时列表空、size 为 0，第一轮判断 0 < 0 直接为假——add 一行都没跑，程序安静结束，列表保持空。选 b 的同学脑内把条件当成了固定目标。确实存在这种死循环的亲戚，但条件恰好相反：**列表初始非空**时（比如先装了一个元素再进循环），i 永远比 size 小一步、边加边比永远追不上，那才是死循环；而本题的空列表一轮都不跑。虫型是「条件读了一个自己正在改变的值」：想追加 5 个，条件就写 i < 5 或用独立计数器——别让裁判（条件）同时当选手（size）。" />

```java
// 意图：打印 2 行 3 列表格的每个元素
int[][] g = new int[2][3];
for (int r = 0; r < g[0].length; r++) {
    for (int c = 0; c < g[0].length; c++) {
        System.out.print(g[r][c]);
    }
}
```

<MultipleChoice id="rt4-l1-2d" question="这段代码的运行表现是？" options={[{id:'a',label:'正常打印 6 个元素'},{id:'b',label:'崩溃'},{id:'c',label:'什么都不打印'},{id:'d',label:'打印 9 个元素'}]} answer={['b']} explanation="2 行 3 列：g.length 是 2（行）、g[0].length 是 3（列）。外层管行却用了列数 3，r 走到 2 时访问不存在的第 3 行，越界崩溃。" />
